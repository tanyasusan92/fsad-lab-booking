## How AI Was Used

### 1. Tech Stack & Architecture Decisions

**Prompt theme:** "I have these skills [MySQL, React, PHP, Node, Tailwind, HTML/CSS/JS]. The brief mandates React frontend + microservices + REST APIs. What's the optimal stack?"

Claude analyzed the assignment brief against my skills and recommended:
- **React + Vite + Tailwind** (vs. CRA / styled-components)
- **Node + Express** (vs. Python/Django, leveraging my JS familiarity)
- **MySQL + raw mysql2 driver** (vs. ORM, after weighing Prisma/Sequelize)
- **JWT-based auth** matching the brief's "simulated token-based" requirement
- **Modular monolith** instead of full multi-process microservices, citing the 7-day timeline

**My decision:** I went with the recommended stack. The reasoning around timeline-vs-architecture (modular monolith as legitimate "logical microservices") was particularly persuasive for a constrained schedule.

### 2. Problem Statement Selection

**Prompt theme:** "Give me 8 problem statement options similar to the sample (school equipment lending), more original."

Claude generated options ranging from blood donation portals to hostel room swapping. I picked **Campus Lab Slot Booking** because:
- Closest in complexity to the sample
- Time-slot booking is more interesting than item lending
- BITS-relevant (fits the "campus" theme grader-evaluators recognize)

### 3. Conflict Detection Logic (My Differentiator)

**Prompt theme:** "What makes a slot truly 'available'? What edge cases should I check?"

Claude proposed a **3-layer conflict detection** that I'd not have thought of unaided:
1. Is the slot blocked for maintenance?
2. Does the slot already have an active booking?
3. **Does the user have ANOTHER active booking at the same date+time elsewhere?**

The third check (user clash) is the differentiator. Most assignments only check layer 2. AI surfaced this from prompting me with: *"What's the typical edge case students miss?"*

### 4. Database Schema Design

**Prompt theme:** "Help me design tables that prevent invalid states."

AI suggested:
- `ENUM` columns for role/status/type — DB-level validation
- `UNIQUE KEY (lab_id, date, start_time)` on slots — prevents duplicate slots
- `ON DELETE CASCADE` on slots — cleanup on lab deletion
- `ON DELETE SET NULL` on `decided_by` — preserves booking history if approver leaves

I implemented all of these. The `INSERT IGNORE` pattern for slot generation (idempotent slot creation) was AI-suggested.

### 5. Boilerplate Generation

The following were generated by Claude with my review:

- All controller files (auth, lab, booking)
- React form components (Login, Signup, LabFormModal, booking modal)
- Swagger JSDoc comments on routes
- Tailwind class strings for UI components

I read every line, modified for my use case (e.g., changing "technician" to "staff" to match brief language), and tested before committing.

## Reflections on AI's Contribution

### Where AI Excelled
- **Boilerplate** — generating consistent, working code for similar patterns (CRUD endpoints, React forms) saved hours
- **Stack research** — comparative analysis of ORMs, deployment options, etc. without me having to read docs for each
- **Catching edge cases** — the user-clash detection layer was AI's most valuable contribution
- **Debugging unfamiliar errors** — diagnosing PATH issues, GitHub auth problems, version conflicts
- **Documentation tone and structure** — README organization, Swagger formatting

### Where AI Was Less Useful
- **Tightly coupled, project-specific bugs** — when the issue depended on an exact file state I had to share. AI sometimes asked me to paste the same content multiple times before pinpointing the issue.
- **Real-time state in my running app** — AI couldn't see my screen, terminal output unless I shared, or what I'd already changed. Required extra communication overhead.
- **Personal style preferences** — AI defaults to verbose, comment-heavy code. I trimmed comments to match my own style.

### How AI Changed My Workflow
- I prompted AI as I built rather than writing pseudocode myself first
- I explained problems out loud (typed) which often led me to solve them before AI replied — the act of explaining was useful in itself
- I treated AI as a senior pair-programmer, not as an oracle. I always read and tested generated code.

### What I'd Do Differently Next Time
- Maintain this log in **real-time** instead of reconstructing — would have richer prompt records
- Push back more on AI when its suggestions felt like overkill (e.g., excessive validation layers for a 7-day project)
- Use AI more for **test case generation** (I tested manually but could have automated)

## Conclusion

AI was a **force multiplier**, not a substitute. It accelerated boilerplate by ~3-4x, surfaced patterns I would have missed (3-layer conflict detection, ENUM constraints, INSERT IGNORE for idempotency), and unblocked me on environment-setup issues that would have taken hours to debug alone.

But the project's design choices (problem statement, scope, what to cut), all manual testing, and integration verification were mine. AI never touched my keyboard — every line of code in the repo was reviewed and intentionally accepted by me before being saved.

The total project effort was approximately **~25 hours over 7 days**. AI assistance probably reduced this from what would have been **~60-70 hours** without it. That's the real value: not eliminating work, but compressing the cycle of *write → test → debug → research → fix* into a more efficient feedback loop.
